# Production OIDC / PKCE design — proposal, not implemented authentication

Vision owns provider choice, hosting, canonical adapter integration and go-live approval. No identity-provider connection or token acquisition was attempted. This design adds no second canonical data source. The only code delivered here is a standalone PKCE S256 helper. The current API accepts a shared synthetic token and MUST NOT be treated as a production identity boundary.

## Recommended flow for the existing dashboard

Use a registered public browser client with Authorization Code + PKCE S256. Choose an OIDC provider supporting a dedicated API audience and an explicit read-only dashboard scope. Register exact HTTPS callback and logout URLs, without wildcard redirects; use a separate localhost development registration. Do not add a client secret to browser code. Do not use implicit or password grants.

1. Before redirect, create a fresh verifier, challenge, state and nonce using Web Crypto in the browser (the Node helper illustrates the server-side equivalent). Store transaction state, verifier, nonce, creation time and an allowlisted return route in short-lived per-tab session storage or equivalent transaction storage, never URLs or logs. Limit transaction lifetime to five minutes and allow a bounded number of pending transactions. Validate the configured provider/issuer and authorization endpoint; never discover them from request input.
2. Send response_type=code, S256 challenge, state, nonce, exact redirect_uri, client_id, audience/resource as required by the provider, and minimal openid/dashboard:read scopes. Avoid requesting profile/email or offline access without an actual need. Those parameters are provider-specific and must be verified against the selected provider.
3. At callback, reject duplicate, missing, unexpected and oversized parameters; match and atomically consume one state transaction before code exchange. Reject expired/replayed transactions and mismatched issuer (authorization-response issuer validation where supported). Exchange the code only at the fixed HTTPS token endpoint with the exact redirect URI and verifier. Do not retry a consumed code after an ambiguous response. Clear URL query parameters immediately. Never redirect to an unvalidated return URL.
4. Validate ID token issuer, signature, audience/client_id, azp when applicable, nonce and time claims through a maintained OIDC client library. An ID token identifies the login and MUST NOT authorize API access. State, nonce and PKCE protect different parts of this flow; none substitutes for the others.
5. Keep short-lived access tokens in memory; never localStorage, query strings, analytics or logs. On reload reauthenticate using the provider session. If persistent sessions later become necessary, Vision should separately decide whether a BFF with server-side tokens and Secure/HttpOnly/SameSite cookies is appropriate; it requires CSRF controls and is outside this candidate. Do not silently add refresh tokens. If explicitly enabled later, require rotation, reuse detection, bounded lifetime and provider support.
6. Send the access token only in the Authorization header to the configured HTTPS API origin. Logout clears local state/tokens and invokes the provider's registered logout flow where supported. Define maximum access-token lifetime and emergency denylist/session-revocation requirements; local logout alone does not revoke already issued bearer tokens.

## API resource-server validation

Replace the synthetic bearer path entirely in a separately reviewed integration. Use a maintained JWT/OIDC library (for example a pinned and reviewed `jose` release) rather than custom signature verification. This candidate adds no such dependency yet. The API must fail startup if production issuer, audience or authorization policy is absent; never fall back to the synthetic token.

- Accept one bounded Authorization header with a single Bearer access token; reject query/cookie tokens and duplicate credentials. Normalize standards-compliant scheme handling in the real bearer parser; this synthetic fixture intentionally uses an exact string.
- Pin the exact HTTPS issuer and API audience, permitted asymmetric algorithms (e.g. RS256/ES256 as selected), token type/provider access-token profile, required exp/iat claims, nbf when present, maximum token lifetime and bounded clock skew (target <=60 seconds). Reject alg=none, HMAC confusion, unexpected azp/client identity, wrong issuer/audience and ID tokens. Treat claims as untrusted until signature and policy checks pass.
- Fetch discovery/JWKS only from configured HTTPS endpoints. Never use token jku/x5u or arbitrary request-supplied URLs. Bound response bytes, network deadlines, cache size and TTL, refresh concurrency and unknown-kid refresh frequency. Support legitimate key rotation; fail closed when no valid cached key can verify a token. Test provider outage, stale keys, missing kid and rotation races. For opaque access tokens, use authenticated provider introspection with explicit fail-closed caching instead of pretending they are JWTs.
- Require stable issuer + subject identity and an explicit allowlist/group/role mapped to `dashboard:read`. Scope alone must not grant every provider user access. Deny by default; filter views and records using the canonical adapter's authorization boundary. Return 401 for invalid authentication and 403 for valid identity lacking permission, without token/claim details. Retain the read-only method boundary independently of identity.
- Apply per-identity and per-network request quotas at the selected trusted gateway/API, with a bounded store; validate trusted-proxy configuration before reading forwarded client IPs. CORS is a browser read policy, never authentication. Permit only the real dashboard origin; keep read-only preflight narrowly scoped.
- Use TLS, HSTS at the HTTPS boundary, log redaction and minimal security audit events (outcome, stable pseudonymous principal, route, request ID; no tokens, codes or personal claims), rotation/incident procedures and dependency patching. Decide CSP for the dashboard separately; the API CSP does not secure dashboard scripts.

## Required acceptance evidence before production

Test an actual provider sandbox and approved hosting boundary: successful login, wrong/replayed/expired state, nonce mismatch, verifier mismatch, authorization error, redirect attacks, code replay, malicious discovery URLs, wrong issuer/audience/algorithm, expired/future token, ID-token substitution, missing scope/role, removed user, tenant crossing, oversized/duplicate credentials, key rotation/outage, logout and revocation delay. Include real browser preflight/callback tests, canonical read-only contract tests, gateway/TLS/slow-client/load tests and failure recovery. None of these provider/hosting integrations is verified by this package's unit tests.
